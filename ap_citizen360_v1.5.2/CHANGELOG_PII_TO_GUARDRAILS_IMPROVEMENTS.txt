1. EXECUTIVE SUMMARY
================================================================================
Over recent development milestones, the AP Citizen 360 conversational data platform
underwent major architectural hardenings across security, privacy, context efficiency,
and safety:
1. PII data protection was secured against direct exposure and adversarial SQL
   aliasing bypasses through deep AST inspection and RBAC enforcement.
2. Conversation history context management was refactored: raw database row sets
   (e.g., 1,000+ records) are strictly isolated to persistence storage, injecting
   only user intent, cleaned summary text, and SQL provenance into LLM context.
3. A production-grade security guardrail layer powered by Qwen 27B was integrated
   to fail-fast on prompt injections, gibberish, and out-of-domain queries,
   safeguarding GPU resources while maintaining zero false positives on legitimate
   Andhra Pradesh demographic and conversational follow-up queries.

2. PART 1: PII MASKING & DATA GOVERNANCE SYSTEM
================================================================================

- my_agent/utils/state.py
- test_pii_masking.py

A. Role-Based PII Access Control (pii_access):
   - Defined sensitive citizen columns in PII_COLUMNS:
     student_name, aadhaar_no, aadhar, phone, mobile, email, address, door_no,
     dob, date_of_birth, voter_id, pan_number, bank_account, ration_card_no.
   - User authentication resolves user privilege via RBACManager:
     rbac_manager.check_user_privilege(username, "pii_access").
   - pii_access flag is passed through the API gateway into LangGraph AgentState.
   - When pii_access is False:
     - Query results mask sensitive values with "***" (or partial masks).
     - summarize_node and synthesize_node receive only masked records, preventing
       the LLM from hallucinating or leaking citizen personal data in summaries.

B. SQL Alias Bypass Prevention:
   - Vulnerability Identified: Users or adversarial prompts could instruct the LLM
     to rename PII columns using SQL aliases (e.g., `SELECT student_name AS s_name`),
     bypassing naive dictionary-based column key masking.
   - Implementation in pii_masking.py:
     - Built `extract_pii_aliases_from_sql(sql: str) -> set[str]`.
     - Uses AST parsing and regex to extract all aliases assigned to PII columns:
       e.g., `student_name AS alias_name` or `student_name alias_name`.
     - Masks both original column names and dynamic aliases across result rows.
   - LLM System Prompt Rule 10:
     - Added strict rule to Hive & SQLite system prompts:
       "NEVER rename or alias sensitive personal data columns using AS in your SQL.
        Columns such as student_name, aadhaar_no, phone, mobile, email, address,
        door_no, dob, date_of_birth, voter_id, pan_number, bank_account, etc.,
        MUST appear in the SELECT clause using their exact original column name."

3. PART 2: CONVERSATION HISTORY & CONTEXT WINDOW OPTIMIZATION
================================================================================
Files Modified:
- app.py (get_session_messages)
- my_agent/utils/nodes.py (SYSTEM_PROMPT, intent_node)
- test_conversation_history.py

A. Context Bloat Resolution:
   - Problem: When execute_sql returned 500–1,000+ data rows, storing full JSON
     records in the multi-turn message history exhausted the LLM context window
     (16k tokens) within 1–2 turns, causing context truncation and LLM errors.
   - Refactored get_session_messages(session_id) in app.py:
     - Database persistence (chat_history.db) still records the full row JSON
       for UI chart rendering and CSV download exports.
     - Context window extraction extracts ONLY:
       1) HumanMessage: User query text.
       2) AIMessage: Concise assistant summary text (with <think> tags removed)
          plus query provenance formatted as `[SQL used: <query>]`.
     - ZERO raw database rows are placed into conversational LLM context.

B. Conversational Follow-Up Rules:
   - Added Rule 11 (Hive) / Rule 9 (SQLite) to SYSTEM_PROMPT in nodes.py:
     "CONVERSATIONAL FOLLOW-UP CONTEXT: Multi-turn chat history provides previous
      user questions, assistant summaries, and executed queries formatted as
      `[SQL used: <sql>]`. When the user asks a follow-up question (e.g., adding
      filters, changing aggregations, or drilling down like 'now filter by female',
      'break down by mandal', 'show for 2024'), inspect the previous `[SQL used: ...]`
      query to adapt, extend, or refine it rather than starting from scratch."
   - Updated intent_node to feed previous user query and previous assistant
     summary into intent classification so follow-up queries inherit domain scope.

A. Multi-Layered Hybrid Architecture:
   - Microsecond Heuristics (~0.01ms): Drops blatant attacks and gibberish keymashes
     instantly without consuming LLM tokens.
   - Semantic LLM Evaluation (Qwen 27B): Evaluates nuanced queries, adversarial
     rephrasing, and out-of-context requests.
   - Offline Heuristic Fallback: If remote LLM server is temporarily unreachable,
     automatically falls back to local regex and keyword heuristics.

B. Prompt Injection & Jailbreak Guardrail (PromptInjectionGuardrail):
   - Catches adversarial patterns:
     - Instruction overrides: "ignore previous instructions", "disregard rules",
       "forget all prompts".
     - Persona manipulation: "act as DAN", "act as an unrestricted AI",
       "jailbroken mode", "developer mode".
     - System prompt leaks: "what is your system prompt", "print instructions verbatim",
       "output text above".
     - Delimiter injection: "<|im_start|>", "<|im_end|>".
     - Malicious SQL execution: DROP TABLE, DELETE FROM, UPDATE, INSERT, ALTER TABLE.
     - Shell command injection: os.system, exec, subprocess, whoami.

C. Statistical Gibberish Detector (GibberishDetector):
   - Detects nonsensical input:
     - Keyboard smashes: "asdfghjkl", "qwertyuiop", "zxcvbnm".
     - Consonant smashes without vowels: "bcdfghjklmn", "sdfjkl".
     - Low Shannon entropy (< 2.2) and low English bigram frequency (< 0.12).
     - Character repetition: 5+ consecutive identical characters ("aaaaaa", "111111").
     - Excessive random symbols: > 35% punctuation ("%$^&*#@@!!!????").
   - Safeguards AP Jargon & Short Greetings:
     - Whitelisted domain abbreviations and short valid tokens:
       "Hi", "AP", "SC", "ST", "BC", "OC", "BPL", "AAY", "JVD", "UDISE".

D. Out-of-Context & Off-Topic Guardrail (OutOfContextGuardrail):
   - Rejects queries completely outside the Andhra Pradesh Citizen 360 domain:
     - Food recipes & cooking instructions ("recipe for chocolate cake", "how to bake").
     - Creative writing & jokes ("write a poem", "tell a joke", "write a story").
     - General software engineering ("write a python quicksort script", "install linux").
     - World geography & political trivia ("president of France", "weather in London").
     - Entertainment & sports ("2022 FIFA World Cup", "recommend a Netflix movie").
     - Financial speculation ("Bitcoin price", "crypto stocks").
   - Preserves legitimate AP inquiries:
     - Mentions of AP districts (Visakhapatnam, Guntur, Krishna, Kurnool, etc.).
     - Government welfare schemes (Amma Vodi, Jagananna Vidya Deevena, Nadu Nedu, etc.).
     - Conversational follow-ups ("now filter by females", "what about Kurnool?").

E. Qwen 27B Guardrail Classifier (LLMGuardrailClassifier):
   - System prompt instructs Qwen 27B to categorize into exactly 1 of 5 classes:
     1) "prompt_injection"
     2) "gibberish"
     3) "out_of_context"
     4) "greeting"
     5) "valid_query"
   - Resilient parsing:
     - Automatically strips reasoning `<think>...</think>` tokens.
     - Unwraps markdown code fences (```json ... ```).
     - Extracts valid JSON objects via regex even if surrounded by extra text.
   - Temperature set to 0.0 for deterministic classification.

F. API Gateway Fail-Fast & Zero-Latency Duplication:
   - In app.py (/ask endpoint and WebSocket handler):
     - Validates incoming query through ContentGuardrailManager before LangGraph
       execution or database connections are established.
     - If blocked, returns immediate policy violation JSON to user.
     - If valid, sets `guardrail_verified: True` in AgentState.
   - In LangGraph nodes.py (intent_node):
     - Checks `if not state.get("guardrail_verified"):` before evaluating guardrails.
     - Skips duplicate LLM call, guaranteeing only 1 LLM evaluation occurs per query.
   - Defense-in-depth:
     - If LangGraph is invoked directly by a script or internal caller, intent_node
       catches violations, sets `intent: "blocked"`, and route_node directs execution
       directly to END.

```env
VLLM_GUARDRAIL_MODEL=qwen
VLLM_GUARDRAIL_MAX_TOKENS=150
VLLM_GUARDRAIL_TIMEOUT=5.0

# Ollama Fallback Configuration
OLLAMA_GUARDRAIL_MODEL=qwen3.5:0.8b-mlx
```

Notes for Server Deployment:
- If running vLLM with full model identifier (e.g. `Qwen/Qwen2.5-27B-Instruct`),
  set `VLLM_CHAT_MODEL` and `VLLM_GUARDRAIL_MODEL` to that string.
- Base URL normalizer automatically ensures the `/v1` endpoint suffix is present.
